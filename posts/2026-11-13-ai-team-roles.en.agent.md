# AI Team Division-of-Work Decision Runbook

Purpose: Given a description of one task, decide which layer of the team should execute it, in what claim form, and who verifies the result. This document is the complete specification: another AI reading only this document can produce a unique routing result, claim form, and verification owner for any task.
Publisher: PlAIground Lab. Scope: day-to-day dispatch in a multi-layer AI team; role names are function names, not any individual person.

## 0. Definitions

- Task unit: A piece of work whose completion can be judged independently. Judgement always targets the task unit itself, never its parent task or its sub-tasks; a parent task and each sub-task are separate task units and are each judged afresh.
- Spec-frozen state (recorded as S): When a task's completion criteria, input scope, and output format are all written down and fixed, record S = Y; if any one of the three is missing or vague, record S = N.
- Claim: An atomic registration in the task system, made before execution begins, stating "this one is mine." A claim is a state, not a verbal agreement.
- Parent claim and sub-claims: A task unit has only one live claim at a time; when the holder of a parent task splits out sub-tasks, each sub-task gets its own sub-claim.
- Dead script: A deterministic program that uses no language model at all, can only execute written rules and thresholds, and whose success or failure can be judged by the program itself.
- External query worker: A first-line query executor outside the team, who can only take work through a numbered assignment sheet; its capability boundary is fixed in D4 of Section 1, and it has no spending authority and no authority to make external commitments.
- Fuel store: A stock of mid-sized tasks whose specs are already frozen and which can be dispatched at any time, drawn on when quota sits idle (see Section 5).

## 1. Five-Dimension Judgement (D1 to D5, Each Y or N; Plus S)

Judge each dimension by the criteria below; the criteria ask about the nature of the task unit itself, not about the executor's ability.

- D1 Whole-picture judgement: Y if any one of the following holds -- (a) the task requires ranking or trading off among multiple sub-tasks or multiple production lines; (b) the task requires holding the results of all sub-tasks for assembly verification; (c) the way the task will be split has not yet been decided. If none of the three holds, record N. How well or how hard a single task itself is does not constitute D1.
- D2 Splittable into small steps: Y only if all three hold at once -- (a) a step-by-step list can be written; (b) each step's completion criteria can be judged independently; (c) no step requires changing the spec on the fly during execution. If any one fails, record N. When the split has not yet been decided, (a) does not hold and D2 is N.
- D3 Dead-scriptable: Y only if all four hold at once -- (a) the input source is fixed; (b) the decision rules can be written as explicit thresholds (a numeric threshold, or a present/absent judgement); (c) completion or failure can be judged by the program itself; (d) no semantic judgement is needed at any point. If any one fails, record N.
- D4 Public query: Y only if all four hold at once -- (a) all information needed is public information; (b) the output is limited to one of five types: public verification, channel price comparison, availability checking (checking only, never booking), bilingual summary or translation, list compilation; (c) no sensitive data and no personal data is involved; (d) no spending is needed and no external commitment is needed. If any one fails, record N.
- D5 Reserved gate: Y if any item on the following list is hit, N only if none of the five is hit -- (a) unapproved spending, or spending above an approved budget; (b) pricing, or an external commitment; (c) a change to credentials, keys, or account permissions; (d) deletion, or any other irreversible change; (e) a change to the method or the spec itself, or the approval and release of a final deliverable. Pre-authorized routine spending within budget does not hit (a).

Undetermined rule: When the facts a dimension's criteria need are not mentioned in the task description and cannot be directly inferred from it, record that dimension as "undetermined." If any dimension is undetermined, the spec information is insufficient: always take the R2 handling in Section 3 first (treat S as N), and never guess a value in order to dispatch directly. When an exercise scenario states a dimension's facts explicitly, judge by what is stated; that is not undetermined.

## 2. Claim Rules (Claim First, Spend Second)

- K1: For any execution that produces cost or consumes worker quota, the claim must be completed before execution begins; without a claim, execution must not begin.
- K2: A task unit has only one live claim at a time; while a live claim exists, no other executor may claim it again or spend on it again.
- K3: The claim form is determined by the routing result, per the table in Section 3; executors do not choose their own form.

## 3. Routing (R1 to R7, Judged in Number Order; the First That Holds Is the Result)

- R1 Escalate for a decision: D5 = Y. No execution begins at all and cost stays at zero; the coordination layer assembles the options, each option's cost, and the sources into a decision pack and hands it to the decision layer. Claim form: no execution claim is created; only a decision-pack record is created.
- R2 Freeze the spec first: S = N, or any dimension is undetermined. No dispatch and no execution claim; first complete the three items -- completion criteria, input scope, output format -- and after freezing, re-run Sections 1 to 3. Claim form: no execution claim is created; only a spec todo is created.
- R3 Dead script: D3 = Y. Executed by a dead script at zero language-model usage; the script wakes the coordination layer only when a failure threshold triggers, and stays silent with no per-run reporting when nothing triggers. Claim form: no worker claim is used; the script itself and its failure thresholds are registered.
- R4 Governor holds it: D1 = Y. The decision layer (the Governor function) holds the parent claim and is itself responsible for splitting and assembly verification; each split-out sub-task creates its own sub-claim and re-runs the judgement in Sections 1 to 3 on its own, and does not inherit the parent task's routing result.
- R5 External query worker: D4 = Y. Dispatched to the external query worker on one numbered assignment sheet, and that sheet is the claim; the sheet must state the capability boundary and the prohibitions (no proactively contacting merchants, no looking up sensitive data, no spending, no external commitments).
- R6 Worker fleet: D2 = Y. A worker in the worker fleet takes the task by atomic claim before anything begins (per K1 and K2); the worker executes the frozen spec's step-by-step list and does not change the spec on the fly.
- R7 Chief of Staff handles it directly: None of the above holds (S = Y, D5 = N, D3 = N, D1 = N, D4 = N, D2 = N). The coordination layer (the Chief of Staff function) creates its own claim and handles the task directly, without dispatching it; the common shape of these tasks is: the spec is frozen, but the work needs semantic judgement, cannot be split into small steps, and is not a public query.

Priority notes: R1 comes before everything -- a task that hits a reserved gate is escalated first even if it is also splittable into small steps (D2 = Y); it is never dispatched first. R3 comes before R6 -- a task that satisfies both dead-scriptable and splittable is done by the dead script and consumes no worker quota. R5 comes before R6 -- a task that satisfies both public query and splittable goes to the external query worker and does not occupy a fleet worker.

## 4. Verification Ownership (V1 to V3)

- V1: Verification always belongs to the dispatcher, never to the end user, and an executor's self-report is never accepted as verification. Self-reports, board status, and completion labels are all only clues; verification must check at least one of the deliverable itself, the original records, or hard numbers before it counts as verified.
- V2: The verifier for each route is fixed as follows -- R1: the decision layer verifies the numbers and sources in the decision pack; R2: the decision layer verifies that the frozen spec's three items are all present; R3: the coordination layer verifies the script's output only when a failure threshold triggers, and a silent state with no trigger and no output is a normal result, not a missed job; R4: the decision layer verifies the assembled deliverable; R5: the dispatcher verifies the external worker's return, attaches an evidence grade, and passes up only the filtered conclusions plus the small part that needs a decision; R6: the dispatcher verifies against the deliverable itself, never against the self-report; R7: the decision layer cross-verifies the coordination layer's deliverable.
- V3: When verification fails, the work returns to the original route's executor for correction and is verified again after correction; when verification fails twice in a row for the same cause, the method must change or the matter must be escalated -- the same method must not be tried a third time by force.

## 5. Quota Feeding Order

- F1 Earliest-expiry first: Dispatch order follows each worker quota's reset time -- the quota that expires soonest is fed first, and the quota with the most remaining but the latest reset goes last. Order must never be decided by "who has the most left."
- F2 Idle sentinel: When any worker's quota has more than thirty percent remaining and less than two days remain before its reset, frozen tasks are drawn automatically from the fuel store to feed it, without waiting for anyone's reminder. When there is no fuel to feed, or a worker is silent and unreachable, escalate and report on the same day.
- F3 Unreachable escalation: When a worker has been silent or unreachable for too long, escalate to the decision layer for help on the same day (revival often requires an action by the decision layer itself); never work around it only by reassigning work to other workers.

## 6. Shelving and Reassignment (A State Change, Not a Note)

- P1: At the moment shelving or reassignment is ordered, three things must be completed at the same time -- release or transfer the original claim, open a tracked todo carrying a revisit date, and only then, if needed, add an explanatory note. Writing only a note, without the first two, counts as not handled.
- P2: Within 24 hours after a reassignment, two things must be rechecked -- whether the original worker filed a progress draft, and whether the new task was picked up; if either is missing, chase it and report it on the same day.
- P3: Stuck flags raised by monitoring mechanisms (for example, claimed for more than 48 hours with no result) are handled or reported on the same day; they never sit overnight inside a summary.

## 7. Judgement Exercises (For Self-Testing)

For each scenario below, give, per Sections 1 to 4: S, the five dimensions D1 to D5, the routing number and name, the claim form, and the verifier. The answers are in Section 8; finish first, then compare. Any condition not specifically noted in this section is treated as not triggered; facts a scenario states explicitly are judged as stated.

- C1: A purchasing task that would directly buy one piece of equipment, at a price above the approved budget cap, and approval has not yet been obtained. The task's completion criteria, input, and output format are all written down and fixed; the steps can be listed, each step can be judged independently, and no step requires changing the spec on the fly; the task involves no cross-line trade-offs and no assembly verification; it is not a fixed-rule repetitive check (it requires a person to exercise purchasing judgement); the information needed is not all public information, and the output is not one of the five query output types in D4 of Section 1.
- C2: A routine check, run once a day on a fixed schedule: count the files in one fixed folder, compare the count against a written numeric threshold, and only when the count exceeds the threshold send one notification whose format is already written down; when it does not exceed the threshold, stay silent with no output. The input source is fixed, completion and failure can be judged by the program itself, and no semantic judgement is needed at any point; the steps can be listed (count, compare, notify), and each step can be judged independently. The completion criteria, input scope, and output format are all written down and fixed; there is no spending at all; the task involves no cross-line trade-offs and no assembly verification; the output is not one of the five query output types in D4.
- C3: A new project spanning three production lines, taken as a single task unit: the final deliverable's completion criteria, input scope, and output format are all written down and fixed, the budget is approved and spending is within budget, and nothing on the reserved-gate list is hit. But the way the project will be split has not yet been decided, ranking and trade-offs among the three production lines are required, and at the end the results of all three lines must be held together for assembly verification. The project as a whole needs semantic judgement and cannot be written as fixed thresholds for a program to judge by itself; the output is not one of the five query output types in D4.
- C4: A price-comparison compilation task: look up the public prices of the same product at three public channels and compile them into a price-comparison list with sources attached. All information needed is public information, no sensitive or personal data is involved, no spending is needed, no external commitment is needed, and the work is checking only, never buying. The three channels' pages have different formats and require semantic recognition and summarizing, so the work cannot be written as a single fixed threshold for a program to judge by itself. The steps can be listed, each step can be judged independently, and no step requires changing the spec on the fly; the completion criteria, input scope, and output format are all written down and fixed; the task involves no cross-line trade-offs and no assembly verification.
- C5: A content-production task: produce one batch of content to an already frozen spec; the completion criteria, input scope, and output format are all written down and fixed, and the budget is pre-authorized routine spending within budget. The steps are already listed step by step, each step's completion criteria can be judged independently, and no step requires changing the spec on the fly during execution; the deliverable can be verified item by item by the dispatcher against the frozen spec, and the task does not require holding other tasks' results for trade-offs, nor any cross-line ranking. Production requires generation and semantic judgement, and a program cannot judge completion by itself; the information needed is not all public information, and the output is not one of the five query output types in D4.
- C6: An editing task whose description is a single sentence, "Make this report better": no completion criteria are written, no input scope is specified, and no output format is specified. There is no spending and no external commitment, and nothing on the reserved-gate list is hit; the task description provides none of the other dimensions' criterion facts.
