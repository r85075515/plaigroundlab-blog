排程被關掉不是缺席，是事故：靜默失效要自己報警

給你的 AI：本篇另備乾淨 Markdown 的 agent 版，讀了就能照著做——中文版・English

前段：寫給人看的故事

有一天清點每日工作時才發現：好幾條每日排程全數處於停用狀態。沒有人下令停用，沒有任何紀錄寫著誰、何時、為什麼把它們關掉，更沒有任何一條排程在被關掉的那一刻出聲。它們就那樣安靜地缺席了好幾天——不是產出做壞了，是產出根本沒有發生，而系統裡沒有一個位置在替「應該發生卻沒有發生」這件事倒數。

排程缺席最危險的地方，是它長得跟沒事一樣。做壞的產出會留下錯誤紀錄，跑到一半死掉的程序會留下半成品，唯獨被關掉的排程什麼都不留：沒有錯誤、沒有紀錄、沒有警示，只有一片安靜。而安靜最容易被讀成正常——直到有人主動去數，才發現缺口已經累積了好幾天。

我們吃過的虧很具體：多條每日排程被發現全數靜默停用，無人下令也無紀錄，錯過的產出只能逐條清點再補發。從那之後規則定版成三段：排程的停用狀態本身就是一個要回報的事件，不等產出缺席才算數；預期產出沒有出現，本身就是事故，不等有人發現才成立；錯過的產出要補發，不準跳過當作沒發生過。

這篇的定版處置分三段。登記在先：每一條排程都要進登記表——名稱、節奏、負責方、預期產出與預定時刻都寫死，沒有登記的排程等於沒有人知道它應該存在。對帳不輟：零 LLM 死腳本每小時把登記表和排程的實際狀態對一次，狀態不是預期啟用、又查無核準暫停紀錄，就是靜默停用，立即升級回報。補發銷帳：重新啟用只是第一步，漏掉的每一份產出逐份補發並驗證，全數補齊才準銷帳。

後段把整套判定寫死：六種處置代碼與優先序、登記表的必填欄位、漏產的判定門檻與核準暫停的成立條件。任何人（或任何 AI）拿到一個排程情境，都能給出唯一處置，不靠猜。

以下為完整 runbook

1. 三個機制：登記表、狀態對帳與補發

  • 登記表：所有排程的清單，每條一筆，必填欄位見第 2 節。登記表是「應該存在什麼」的唯一依據；不在登記表上的排程，停用了也不會有人發現。
  • 狀態對帳：一個零 LLM 的死腳本，每小時做一件機械的事——逐條讀取排程的實際狀態與最近執行紀錄，和登記表的預期比對，符合升級條件就發出回報。它便宜、固定，而且不會因為「看起來還好」就放水。
  • 補發：排程失效期間漏掉的預期產出，逐份補做並驗證。補發的對象是產出本身，不是把排程重新打開就算數；重新啟用與補發是兩件事，兩件都做完才談銷帳。
  • 核準暫停的位置：排程可以被正當停用，但必須先有明文核準、留下紀錄、寫明覆核日期。有核準的停用是暫停，沒有核準的停用是事故，兩者只差一筆紀錄，處置完全不同。

2. 登記表必填欄位

  • 名稱：排程的唯一名稱，寫到能在排程系統裡直接找到的程度。
  • 節奏與預定時刻：多久跑一次、預定在什麼時刻產出。漏產的判定要靠這一欄，沒有預定時刻就沒有「遲到」可言。
  • 負責方：這條排程出事時由誰處置、升級要通知到哪一層。
  • 預期產出：每次執行應該產出什麼、產出放在哪裡、怎麼驗證它真的出現了。
  • 缺任一欄位，這條排程視為未登記完成：先補齊登記，才談對帳與判定。

3. 判定代碼與優先序

對每個情境依序檢查，取第一個成立的代碼：

  1. C 復原銷帳：排程曾失效（靜默停用或漏產），現已重新啟用，且失效期間漏掉的每一份預期產出都已補發並驗證完成 → C，本案銷帳，本輪結束。
  2. E 靜默停用升級：排程的實際狀態為停用，且查無核準暫停紀錄（沒有明文核準、沒有停用紀錄、或沒有覆核日期，任一缺失即算查無）→ E，立即升級回報負責層級，記為靜默停用事件，不準默默重新打開了事。
  3. M 漏產待補：排程目前為啟用狀態，但有一份以上的預期產出已逾漏產門檻（預定時刻加六十分鐘寬限，見第 4 節）仍未出現，且尚未全數補發驗證 → M，逐份清點漏產、排入補發，補齊前本案保持開啟。
  4. A 核準暫停：排程的實際狀態為停用，且核準暫停三項齊備（明文核準、停用紀錄、覆核日期，見第 5 節）→ A，照覆核日期追蹤，不升級、不要求補發暫停期間的產出。
  5. R 讀取失敗待查：排程的實際狀態或執行紀錄讀取失敗（權限不足、介面錯誤、紀錄缺失到無法判定狀態），以致無法確認它是啟用還是停用 → R，照讀取失敗回報並重試讀取，不準當成停用、也不準當成正常。
  6. W 正常運行：排程為啟用狀態，最近一份預期產出已在寬限內出現並驗證存在，沒有漏產、沒有未銷帳的失效事件 → W，保持每小時對帳節奏觀察，不提前警示。

4. 證據規則

  • 狀態證據只認排程系統裡的實際狀態與執行紀錄。負責方說「應該還在跑」、畫面看起來正常，都不算證據。
  • 漏產門檻寫死：預定時刻過後六十分鐘寬限屆滿，預期產出仍未出現且無法驗證存在，即成立一份漏產。寬限內產出未出現，不判漏產，照 W 觀察。
  • 補發證據只認產出本身：補發的每一份產出要能被打開檢查、驗證內容對得上它原本該產出的東西，才算補發完成；只補標題、只補空殼，不算。
  • 讀不到不等於不存在：狀態或紀錄讀取失敗是讀取失敗事件，照 R 回報；不準把讀不到寫成「查無異常」，也不準寫成「確認停用」。

5. 誠實邊界

  • 核準暫停三項缺一不可：明文核準（誰核準的、核準停用哪一條）、停用紀錄（何時停用、原因為何）、覆核日期（何時重新檢討要不要恢復）。缺任一項，照 E 靜默停用判定，不照 A。
  • 暫停期間的產出不補：核準暫停期間本就不該有產出，該期間的缺席不算漏產、不要求補發；但暫停屆滿覆核日期仍未恢復、也未展延者，自覆核日期起的缺席照漏產與靜默停用的規則另案判定。
  • 重新啟用不自動銷帳：靜默停用被發現後，就算立刻重新啟用，只要漏產還沒補齊，照 M 保持開啟；全數補發驗證完成，才照 C 銷帳。
  • 對帳只報事實：對帳腳本回報的是「狀態為停用且查無核準紀錄」「某份產出逾寬限未出現」這些事實，不判定原因、不判定責任；原因由負責方在收到升級後回報，處置照代碼走。

6. 常見錯誤清單

  • 把缺席當沒事：排程被關掉後一片安靜，安靜被讀成正常，缺口累積好幾天才被清點發現。
  • 只重開不補發：發現停用後把排程重新打開就報告「已修復」，漏掉的產出永遠缺席，帳面上卻已經銷帳。
  • 停用不留紀錄：正當的維護停用沒有寫核準與覆核日期，事後和靜默停用長得一模一樣，只能照事故處置。
  • 對帳燒 LLM：每小時喚醒一個 AI 來「看一眼」排程狀態，預防措施自己變成用量大頭；對帳該是零 LLM 死腳本，只在觸發時才通知人。
  • 讀不到就寫正常：狀態查詢失敗時回報「本小時無異常」，把讀取失敗藏成正常，是靜默失效最常見的共犯。
