# set -e 靜默處決——取證與防禦 Runbook

用途：shell 配方在嚴格模式下無訊息死亡時，執行判定、定位、修復與驗證。本文件是完整規格：另一個 AI 只讀本文件，即可對任意死亡現場做判定、指出下一步，並寫出正確的計數與防禦程式碼。
發布者：PlAIground Lab。適用範圍：以 bash 執行、開啟 `set -e` 的長任務配方。

## 0. 定義

- 嚴格模式：配方開啟 `set -e`；管線另開 `pipefail` 時，管線任一段失敗，管線整體回傳該失敗狀態。
- 命令替換賦值：形如 `_n=$(指令 ...)` 的語句，其結束狀態等於命令替換內最後指令的狀態；該狀態非零時，`set -e` 視賦值失敗並立即結束 shell，不執行後續任何一行。
- 路徑模式未展開：某個 glob 匹配不到檔案時，shell 把模式字串原樣傳給指令；`ls` 收到不存在的路徑會以結束碼 2 失敗。
- 靜默處決：因上述機制死亡，且死亡前未印出任何錯誤訊息的狀態。

## 1. 三徵兆判定（全數成立才成立）

- S1 紀錄停在上一行：紀錄最後一行是正常進度訊息，其後原始碼下一行應產生的輸出完全缺席。
- S2 結束碼非零：執行器回報的 EXIT_CODE 不是 0。
- S3 無錯誤遺言：全份紀錄搜尋 `FATAL`、`error`、`Traceback` 皆無命中。

判定規則：
- S1＋S2＋S3 全數成立 → 分類為「疑似靜默處決」，直接進第 2 節；禁止先查資料、GPU、網路或外部服務。
- 任一不成立 → 不是本規格的原型，分別處理：有錯誤訊息者照訊息查；結束碼為 0 者查產出完整性，不查死亡原因。

## 2. 定位三問（依序執行，前一問有結果才進下一問）

1. Q1 trap／行號：找出紀錄最後一行對應的原始碼位置，看其下一行；該行若含賦值加命令替換、管線或子 shell，即為第一嫌疑行。若配方有 ERR trap，先採用 trap 印出的行號。
2. Q2 二分註解：對嫌疑區段做二分——註解後半段或在中點加 `exit 0`；存活則嫌疑在後半段，死亡則在前半段；重複二分直到縮小為單一行。
3. Q3 語法／最小重現：對嫌疑行執行 `bash -n`（只查語法）；再造最小資料重現——例如只含單一副檔名的目錄配上雙副檔名計數行。最小重現能穩定重現死亡，且把觸發條件改掉（如補上另一副檔名的檔案）即存活，才算定位完成。

三問全走完仍未定位 → 才可升級查環境與外部依賴，且紀錄必須附上三問各自的結果。

## 3. 修法 A：計數一律用 find（硬規則）

禁用寫法：

```bash
_n=$(ls data/*.jpg data/*.png | wc -l)
```

唯一核准寫法（目錄與副檔名依需求代入，結構不變）：

```bash
_n=$(find data -maxdepth 1 -type f \( -name "*.jpg" -o -name "*.png" \) | wc -l)
```

原理：`find` 對「某副檔名為 0 個」回傳正常結束（結束碼 0、少列幾筆）；`ls` 對任一不存在路徑回傳結束碼 2，並在嚴格模式下觸發第 0 節的處決鏈。凡是列檔案再計數，一律用本寫法。

## 4. 修法 B：防禦模板（只用於新寫或重寫的配方）

開頭固定兩行：

```bash
set -euo pipefail
trap 'echo "FATAL: line $LINENO, exit $?" >&2' ERR
```

配套三條：
- 必填變數在開頭集中檢查；選填變數給明確預設值。
- 所有下載指令加 `--fail`，例如 `curl --fail -o out.bin URL`；HTTP 4xx／5xx 必須在下載當下以非零碼失敗。
- ERR trap 只負責留遺言（行號加結束碼），不准在 trap 內吞掉錯誤或改寫結束碼。

邊界：已驗證通過的配方不回改、不補 trap；套用本模板即視為重寫，必須重新跑完整驗證。

## 5. 驗證（修完必做）

1. 用第 2 節 Q3 的最小資料重跑修後的配方：計數結果必須等於目錄內實際檔案數，且結束碼為 0。
2. 故意製造一次失敗（例如必填變數留空）：紀錄中必須出現一行 `FATAL: line <行號>, exit <非零碼>`；沒有這行，防禦視為未生效。
3. 把三徵兆、命中行號、觸發條件、修法類別（A 或 B 或兩者）、驗證結果寫成四欄紀錄，事故才算結案。

## 6. 禁止事項

- 禁止為了避開靜默處決把 `set -e` 整個關掉。
- 禁止用 `ls` 加 glob 做任何計數或存在性判斷。
- 禁止在未完成三徵兆判定前，先把事故歸因於資料、GPU 或網路。
- 禁止回改已驗證配方來補防禦。

## 7. 判定練習（自測用）

對下列現場，依第 1 節給出分類（疑似靜默處決／非本規格原型），若屬原型再給第一步動作；答案在第 8 節，先做完再對照。

- C1：紀錄停在一行正常進度訊息，EXIT_CODE 為 2，全紀錄搜不到 FATAL 與 error；下一行是雙副檔名計數賦值，資料目錄只有單一副檔名。
- C2：紀錄最後一行是明確的 CUDA out of memory 錯誤，EXIT_CODE 為 1。
- C3：紀錄停在正常進度訊息，EXIT_CODE 為 0，但產出目錄少了兩個檔案。
- C4：紀錄停在正常進度訊息，EXIT_CODE 為 1，搜不到任何錯誤字串；下一行是把設定檔複製到目錄的 `cp` 指令，沒有命令替換、沒有管線。
- C5：某配方計數寫成在單一副檔名目錄執行 `ls` 雙模式計數，尚未上線，問應如何改寫。
- C6：一條已驗證通過、穩定運行中的舊配方沒有 ERR trap，問是否應立刻回頭補上。

## 8. 參考答案

- C1 → 疑似靜默處決（S1、S2、S3 全數成立）；第一步走 Q1：嫌疑行就是計數賦值行；修法用第 3 節的 `find` 寫法。
- C2 → 非本規格原型（S3 不成立：已有明確錯誤訊息）；照錯誤訊息本身處理，不走定位三問。
- C3 → 非本規格原型（S2 不成立：結束碼為 0，沒有死亡）；查產出完整性，不查死亡原因。
- C4 → 疑似靜默處決（三徵兆全數成立；嫌疑行不限於賦值行，任何在嚴格模式下非零結束又不印訊息的指令都可能）；第一步走 Q1 標記 `cp` 行，再用 Q2、Q3 縮小與重現（例如來源路徑不存在）。
- C5 → 改寫為第 3 節唯一核准寫法：`find <目錄> -maxdepth 1 -type f \( -name "*.jpg" -o -name "*.png" \) | wc -l` 的結構；禁止保留 `ls` 寫法上線。
- C6 → 不回改（第 4 節邊界）；防禦模板只用於新寫或重寫，舊配方要動就走重寫加完整驗證流程。
