把 AI 代理人常駐記憶從 101 KB 砍到 20 KB 卻不失憶：漸進式揭露與防復胖哨兵實戰

給你的 AI：本篇另備乾淨 Markdown 的 agent 版，內含可直接跑的程式碼與驗收指令——中文版・English

一、為什麼 101 KB 的「超完整記憶檔」反而讓 AI 變笨？

多數人調教自治型 AI 代理時都有同一個反射動作：只要系統踩過一次坑，就在系統提示或常駐 MEMORY.md 尾端補一段「以後永遠記得這樣做」。幾週下來，三個常駐開機必讀檔（操作手冊、長期記憶、工具索引）悄悄膨脹到合計 101.2 KB。

看起來很有安全感，實測卻同時帶來三個反效果：

  • 每一輪都重播歷史故事：光喚醒模型打一句招呼，就要先吞下約 25,000+ tokens 的陳年規則與細節，延遲明顯變慢、免費額度視窗幾輪就見底。
  • Middle-Context 失憶（Lost in the Middle）：當所有領域的操作細節都塞在同一個起動脈絡裡，真正的硬紅線反而被無關段落稀釋。
  • 誰都不敢刪，越補越亂：人工直接開刀刪除舊條目，很容易把已經定版的埠號、驗收條件或帳號限制一起砍掉，造成跨週失憶。

解方不是靠模型記性，而是做一套 「指標驅動＋按需載入＋確定性預算哨兵」 的漸進式揭露（Progressive Disclosure）架構，把常駐檔案壓縮 80% 到 20.4 KB，同時 100% 保留可追溯的執行細節。

二、瘦身前後實測數據對比

指標 瘦身前（大鍋炒常駐檔） 瘦身後（指標索引＋5 份 Runbook） 實測變化
常駐檔案總容量 101.2 KB（約 25.3K tokens） 20.4 KB（約 5.1K tokens） -79.8% 起動載入量
核心憲法＋規則檔（AGENTS） 74.7 KB 8.9 KB -88.1%，紅線密度拉高
長期記憶檔（MEMORY） 25.7 KB 10.7 KB -58.4%，僅留真值與指標
領域細節載入方式 每輪無條件全量灌入 5 份 runbooks/*.md 按任務條件讀取 無關領域 0 B 浪費
數週後防復胖防線 無（全靠人工自律） 0-Token Budget Watchdog + CI 閘門 超限即於 PR 階段阻擋

四、核心程式碼與配置（已脫敏，可直接取用）

1. 宣告式預算規則與指標索引（YAML 規格）

# context_budget.yaml — 引擎與上限完全分離，零硬編碼
boot_files:
  - path: AGENTS.md
    max_bytes: 12288     # 硬上限 12 KB
    max_lines: 220
  - path: MEMORY.md
    max_bytes: 14336     # 硬上限 14 KB
    max_lines: 260

pointer_routes:
  - trigger: "deploy | pages | release"
    load: "docs/runbooks/deploy-and-smoke.md"
  - trigger: "schema | spreadsheet | ingest"
    load: "docs/runbooks/data-pipeline.md"
  - trigger: "budget | quota | incident"
    load: "docs/runbooks/ops-guardrails.md"

2. 0-Token 防復胖哨兵腳本（Python 標準庫，可進 CI）

#!/usr/bin/env python3
# Zero-token watchdog enforcing hard byte/line budgets on always-on agent files.
from pathlib import Path
import json
import sys

# 若不引入 PyYAML，直接讀 JSON 版規則即可維持 0 依賴
BUDGETS = {
    "AGENTS.md": {"max_bytes": 12288, "max_lines": 220},
    "MEMORY.md": {"max_bytes": 14336, "max_lines": 260},
}

def check_repo_budgets(root: Path) -> int:
    failures = []
    for rel, limits in BUDGETS.items():
        target = root / rel
        if not target.exists():
            failures.append(f"MISSING: {rel}")
            continue
        raw = target.read_bytes()
        lines = raw.decode("utf-8", errors="replace").splitlines()
        if len(raw) > limits["max_bytes"]:
            failures.append(f"OVERSIZE: {rel} = {len(raw)} B > {limits['max_bytes']} B (move details to runbooks/)")
        if len(lines) > limits["max_lines"]:
            failures.append(f"OVERLINE: {rel} = {len(lines)} lines > {limits['max_lines']}")
        else:
            print(f"OK: {rel} ({len(raw)} B, {len(lines)} lines)")

    if failures:
        for msg in failures:
            print(f"FAIL: {msg}", file=sys.stderr)
        return 1
    return 0

if __name__ == "__main__":
    raise SystemExit(check_repo_budgets(Path(".")))

3. GitHub Actions 防復胖閘門（僅在關鍵檔案異動時觸發）

name: Agent Context Budget Gate
on:
  pull_request:
    paths:
      - "AGENTS.md"
      - "MEMORY.md"
      - "docs/runbooks/**"

jobs:
  verify-budget:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run 0-token budget & link integrity check
        run: python3 scripts/context_watchdog.py

五、實際踩過的 3 個地雷與修補紀錄

  1. 把「真值」順手刪掉或換成模糊佔位符：早期瘦身最容易犯錯的，是把常駐檔裡的主機位址、Sheet ID、正本 URL 一併搬走卻沒在索引檔留可點擊識別碼，結果 AI 每次都猜錯或讀到舊副本。鐵律：所有「單一真實來源（SSOT）」的 ID、定版數字與紅線都必須以精簡真值留在索引檔裡，搬走的只限操作步驟與案例說明。
  2. 沒有保留完整可回滾快照就原地覆寫：曾因一次性合併重寫多段文字，事後對帳才發現一條邊緣情境規則被誤刪。解法：瘦身必須分波進行，且在覆寫前先把原始檔與 sha256 雜湊封存備份，確保隨時能做逐行 diff 回溯。
  3. 只做一次性大掃除、沒設自動化預算閘門：手動瘦身撐不過兩週就會被「只是多補三行註解」慢慢打回原形。唯有把 max_bytes 與 max_lines 寫進每次 PR 必跑的 0-token 檢查腳本，超限時強迫執行者把細節抽進 docs/runbooks/，系統才會長期維持在 20 KB 水位。
