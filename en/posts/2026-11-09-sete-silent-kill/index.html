The Script Died in Silence: Forensics and Defense Against set -e Silent Kills

For your AI: this post ships with a clean-Markdown agent edition — read it and follow along: English · 中文版

Part One: The Story, for Human Readers

In PlAIground Lab's automation pipelines, one kind of death is the hardest to investigate: a script stops halfway, its log ends at the previous line, and there is no error message, no stack trace, nothing at all — only a non-zero exit code. The first time it happened, every instinct in the team was wrong. We suspected corrupt data first, then the GPU, then the network — and only after burning half the investigation did we find the culprit: the safety mechanism the script itself had switched on, set -e.

Here is what happened. A model-training recipe first had to count how many images were in a dataset, and it did so by listing two filename extensions together and counting the lines. The dataset held 25 images, every one of them with the same extension; the other extension matched zero files. So the shell passed the unmatched pattern, unexpanded, to ls; ls failed with exit code 2; and that line was an assignment statement hiding a command substitution. The recipe ran under set -e with pipefail, the assignment inherited the failed status of the command substitution, and the shell exited on the spot — printing nothing. That line never even wrote its own log entry; the previous line was the end of the entire log.

That is the whole anatomy of a "silent kill": not a logic bug, not a broken environment, but one seemingly harmless counting line that, for one particular shape of data, triggers the instant-death clause of strict mode — and dies without leaving a single word behind.

We eventually turned this class of incident into a fixed forensics-and-defense spec. The conclusions come first; the complete runbook follows.

First, when the three signs are all present, assume a silent kill first. The log stops at the previous line, the exit code is non-zero, and no FATAL or error string appears anywhere in the log — when all three hold at once, do not start by suspecting data, the GPU, or the network. Assume the recipe was executed by set -e, and walk the three localization questions. That one reordering saves the most expensive first half-hour of every incident.

Second, localization asks only three questions. Question one, the trap: what was the next line after the log's last line supposed to do? Question two, bisection: comment out the suspect region half by half until the single line that kills the shell is isolated. Question three, syntax: run bash -n and a minimal reproduction on the suspect line, and confirm whether this is a syntax problem or a runtime-status problem. Only when all three questions fail to localize it do you go back and investigate the environment.

Third, every new recipe opens with a defense, so the next death can speak. The defense is not to switch set -e off — strict mode stops far more real errors than it ever mis-kills. The defense is three things: add an ERR trap, so a failure at least prints a line number and an exit code; give key variables defaults or required-value checks, so an undefined variable does not explode in a strange place mid-script; and add --fail to download commands, so an HTTP error surfaces as a non-zero code on the spot instead of feeding an error page downstream as if it were a result. There is also one dedicated iron rule: never count with ls plus filename patterns — count with find and file-type conditions instead. When nothing matches, find simply returns 0 and exits normally; it does not kill the whole script because one extension happens to be absent.

Fourth, never retro-edit a proven recipe. The defense is added only to newly written or rewritten recipes. Every line of a recipe that has already run and passed acceptance is an asset; going back to "harden it while you are there" can silently change its behavior. If you want to change it, treat it as a rewrite: re-verify it completely and keep a fresh record.

The more automation you run, the more common this silent death becomes, because strict mode exists precisely to "die early rather than carry an error downstream." Our answer is not to loosen the mode. It is to make every death leave at least one line behind, and to hard-code the forensics order, so the next person on duty — or the next AI — does not have to start by suspecting the GPU.

The second half of this post is the complete spec: the three-sign decision table, the execution steps for the three localization questions, a line-by-line reading of the defense template, a right-versus-wrong comparison for counting code, and six scenario judgment exercises. Lift it wholesale onto any pipeline that runs long jobs under shell strict mode.

The Complete Runbook Follows

1. The Prototype Incident (De-identified Reproduction)

  • The recipe ran under strict mode at its outer layer: set -e, with pipefail enabled for pipelines.
  • The counting line was written as:
_n=$(ls data/*.jpg data/*.png | wc -l)
  • The shape of the data: all 25 files in the directory were .jpg; the number of .png files was 0.
  • What happened, step by step: data/*.png matched no file, so the shell passed the unexpanded pattern to ls verbatim; ls failed with exit code 2 because one of its paths did not exist; the pipeline returned failure under pipefail; the assignment statement's status equaled the status of its command substitution; set -e judged the assignment failed, and the shell exited immediately, running no further logging.
  • What an observer sees from outside: the log stops at the line before the counting line; the overall exit code is 2; the log contains no FATAL and no error string.

2. The Three-Sign Decision (Decide First, Then Act)

Only when all three hold do you classify the incident as a "suspected silent kill":

ID Sign How to check
S1 The log stops at the previous line The log's last line is a normal progress message, and the output the following line should have produced is entirely absent
S2 The exit code is non-zero The EXIT_CODE reported by the runner is not 0
S3 No last words Searching the whole log for FATAL, error, and Traceback returns no hits

Once the classification holds, the discipline is: localize with Section 3 first. Do not start by suspecting data, the GPU, the network, or an external service.

3. The Three Localization Questions (Execute in Order)

  1. The trap / line-number question: What is the next line of source after the log's last line? Does it contain an assignment plus a command substitution, a pipeline, or a subshell? If the recipe has an ERR trap, read the line number the trap printed first.
  2. The bisection question: Cut the suspect region in half — comment it out, or exit early with exit 0 to prove the script survives — and keep halving until the region shrinks to a single line.
  3. The syntax and minimal-reproduction question: Run bash -n on the suspect line to rule out a syntax problem; then reproduce it locally with minimal data (for example, a directory holding only one extension) and confirm the trigger is the shape of the data, not the environment.

If all three questions still fail to localize the failure, only then escalate to the environment and external dependencies, and write the results of the three questions into the record.

4. The Defense Template (New or Rewritten Recipes Only)

Every recipe opens, fixed, with:

set -euo pipefail
trap 'echo "FATAL: line $LINENO, exit $?" >&2' ERR

Line by line:

  • set -euo pipefail: stop on any failed command, stop on any undefined variable, and count a pipeline as failed if any segment of it fails.
  • The ERR trap: at the moment of failure, leave at least one log line carrying the line number and the exit code, so the next death can speak; the trap itself does not change the exit code and does not swallow the error.
  • Key variables: check required variables together at the top, and give optional variables explicit defaults, so no undefined state flows into the middle of the script.
  • Download commands: always add --fail (for example, curl --fail), so an HTTP 4xx/5xx fails with a non-zero code at download time instead of saving an error page as a result and feeding it downstream.

Boundary: never retro-edit a recipe that has passed verification. Applying this template counts as a rewrite, and a rewrite goes through complete verification again.

5. Counting Code, Wrong and Right

The wrong way (banned):

_n=$(ls data/*.jpg data/*.png | wc -l)

The right way:

_n=$(find data -maxdepth 1 -type f \( -name "*.jpg" -o -name "*.png" \) | wc -l)

Why: when one extension is absent, find simply lists fewer entries and still exits 0; ls, by contrast, fails with a non-zero code because one of its paths does not exist, and under strict mode it takes the whole script down with it. For any "list files, then count them" need, always use the find version.

6. Closing Record

For every suspected silent-kill incident, record four fields: whether the three signs were all present; the line number the localization landed on and its trigger condition; whether the fix changed the idiom or added the defense; and how it was verified (whether the minimal reproduction moved from failing to passing). A fix with no record does not count as closed.
