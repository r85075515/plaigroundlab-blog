The Watchdog That Nearly Resurrected Finished Tasks: State-Machine Hygiene

For your AI: this post ships with a clean-Markdown agent edition — read it and follow along: English · 中文版

Part One: The Story, for Human Readers

We run a fleet of AI workers, and its tasks are managed as files: to-do tasks live in pending/, claimed tasks in claimed/, and finished results in done/. To stop a task from being stuck forever when a worker claims it and then dies, we keep a watchdog: it scans claimed/ on a schedule, and anything that was claimed long ago with no follow-up gets moved back to pending/ so someone else can pick it up.

Sounds simple. Then, within two days, it nearly caused two serious accidents — and both times, only luck prevented one.

The first time (2026-10-22). The watchdog did the math by the rules: 52 tasks in claimed/ had "been claimed for a very long time," so all 52 should be moved back to the to-do list. Fortunately, every one of those move-back writes was rejected by the server (HTTP 422) — because pending/ already contained archived stubs with the same names, and the new files couldn't be written over them. Afterwards we opened all 52 files one by one, and every single one was a task that had long been finished: when a worker completes a task, it writes the result into done/, but a residual copy remains in claimed/ — and its header plainly read "completed and archived," complete with a completion time and a PASS verdict. The watchdog only ever looked at "claim time"; it never opened a file to read its contents. If that 422 hadn't blocked it that day, 52 finished tasks would have been "resurrected" and run all over again, and their completion records would have been overwritten.

The second time (2026-10-23). We had already fixed the first lesson: read the file's contents before moving anything back, and skip anything carrying a completion marker. The very next day, the watchdog picked out 13 more tasks to move back — this time they were residual copies in an old format: the workers had never updated the copy in claimed/ after finishing, so there was no completion marker and no completion time, and the format check passed them clean through. But all of them had results in done/; they were finished tasks. This time the lifesaver was an API rate limit (HTTP 403): the move-back never actually executed. Twice in a row, it wasn't our design that saved us — it was someone else's error messages.

A bonus landmine from the same period: the workers' claim-time strings carried a region suffix (something like (Phoenix)), which made the standard time parser blow up and return null, and the watchdog nearly misjudged a batch of perfectly normal tasks as "unparseable zombies." The fix was to strip the trailing parenthesized suffix before parsing.

The final rule fits in one sentence: the format check is a necessary condition; whether a result exists in done/ is the sufficient condition — a task may be moved only when both pass. Before any move-back, build an index of the task IDs in done/ from the full tree listing; any ID found in there is treated as residual and skipped, unconditionally. Add a dry-run list before moving, and a recorded reason for every move, and the watchdog has never caused friendly fire since.

The second half of this article is the complete specification of this "safe reclaimer": scanning, time parsing, the dual-gate checks, the dry-run list, execution and auditing — ready to lift into any system that manages tasks with files or queues.

The Complete Runbook Follows

1. The Problem Model

A file-based task system has three state directories: pending/ (to do), claimed/ (claimed), and done/ (completion results). The reclaimer's job is to move "claimed, then lost contact" tasks back to pending/. The danger: a file in claimed/ is not reliable evidence of claim state — the completion flow leaves residual copies behind, and those residuals come in more than one format. Using a single signal (claim time) to drive a destructive move will eventually injure finished tasks.

2. The Reclaim Decision: Three Gates, All Must Pass, in Order

  1. Time gate: claimed_at parses successfully, and the elapsed time since then exceeds the stuck-task threshold (this system uses 48 hours).
  2. Content gate: read the full file — if any completion marker appears (a completion header, or a done_at field, or a completion-verdict field), skip it, with the reason recorded as residual-with-marker.
  3. Result gate: build a complete index of done/ (the set of task IDs, obtained in one pass from the version-control tree listing — do not probe file by file). If the ID is in the index, skip it, with the reason recorded as residual-with-result.

Only a task that passes all three gates (old enough, no completion marker, no result in done/) is genuinely stuck.

3. Time-Parsing Hygiene

  • Normalize time strings first: strip any trailing parenthesized annotation (full-width and half-width parentheses both count — a region-name suffix, for example), then hand the string to the ISO parser.
  • A parse failure does not mean "stuck": file it under the unparseable category — report it, never move it. Treating a parse failure as "very old" is a shortcut to friendly fire.

4. Execution Discipline

  • Dry run first: produce the candidate list first (ID, claim time, each gate's result, planned action), and let a human or an upstream system review it before executing; even for automatic execution, keep the dry-run list on file.
  • Record every item: one line per move — ID, original path, new path, the three gates' results, time. Skipped items get their reasons recorded too.
  • Never overwrite: if a file with the same name already exists in the target directory, stop and report; do not force the write. (The first accident in this article was saved exactly by a name collision refusing the write — but that was luck; the proper practice is to check yourself first.)
  • Cap the volume: set a per-round move limit (for example, 20 items); if the candidate count is abnormally high (for example, more than 5 times the usual), report before executing — when a large number of "stuck tasks" appears all at once, it usually means the judging logic is broken, not that every worker died.

5. Acceptance Checklist

Given a fixture directory with four kinds of files, one of each:

  1. Finished, new-format residual (has a completion marker) → must be skipped.
  2. Finished, old-format residual (no marker, but done/ holds a result with the same ID) → must be skipped.
  3. Genuinely stuck (old enough, no marker, no result in done/) → must be moved back.
  4. Freshly claimed (under the threshold) → must be left alone; a normal task whose time string carries a region suffix → must parse correctly and not be misjudged.

Only when all four behaviors are correct does the reclaimer qualify.

6. General Lessons

  • Destructive automation must check ground truth: before deleting, moving, or overwriting, ask the "where results live" area, not the "self-reported state" area.
  • Being saved by error messages twice is the design asking for help: 422 and 403 were both someone else's brakes; install your own.
  • Write necessary and sufficient conditions separately: whether the format looks finished (necessary) and whether a result actually exists (sufficient) are two different kinds of evidence, with different jobs; neither may impersonate the other.
