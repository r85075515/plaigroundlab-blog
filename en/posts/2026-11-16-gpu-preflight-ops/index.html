Verify Before You Boot: Cloud GPU Operations Discipline

For your AI: this post ships with a clean-Markdown agent edition — read it and follow along: English · 中文版

Opening: The Story, Written for Humans

A cloud GPU is a machine that burns money by the hour. Booting the wrong one, leaving one running idle, or booting one whose GPU cannot actually be used all convert money directly into waiting. This discipline was bought one rule at a time, through repeated boots, stalls, and reboots, and its core fits in one sentence: verify the goods before you hand over any task; confirm the output before you shut down — and shut down means terminate, not stop.

Lesson one is the image and the startup command. An official image ships its own startup script, which brings up remote login and initialisation. Put one seemingly harmless "sleep and do not exit" line in the startup-arguments field and it overwrites the image's own startup script entirely: the machine looks alive and nothing has initialised. The rule is simple: use the official image and leave the startup arguments empty. If the machine must stay up, rely on the fact that it is long-running by nature, not on a command you injected.

Lesson two is where the Python environment lives. A network disk is convenient, and models and data belong on it; but build a Python virtual environment on that same network disk and a program stalls at the very step of loading its libraries — the tell is that even the lowest-level system tools stall, which means the problem is not Python at all, it is "something is reading files off the network disk". The rule: use the system Python, install packages onto the container's local disk, and let the network disk hold only models, datasets, and outputs.

Lesson three is capacity. When the datacenter your disk is bound to has no stock, dry-waiting is the most expensive option: check capacity first, and if there is none, boot a machine with no disk attached instead, pull the models again from public sources, upload the results, and delete the machine at once. Waiting for a machine that is not coming is never cheaper than pulling a model one more time.

Lesson four is the three boot checks. A machine showing "running" does not mean its GPU is usable: the device list must show the card, the compute library must report the GPU as available, and disk space must read normally — all three must pass before any task is handed over. We have seen a package installer pull a compute version newer than the host driver, making the GPU-available check return false outright; the second of the three checks exists for exactly that case, and failing fast is far cheaper than a task dying halfway.

Lesson five is closing. After the work is done and the output is confirmed saved, terminate — do not stop: a stopped machine still bills for disk and storage. After terminating, list the machines once more and confirm with your own eyes that it is gone, and record this machine's cost in the version log. Idle is the same: past fifteen minutes idle, close it — a running unused machine is renting air.

Last is failure discipline: the same error, retried twice and still failing, means stop, send the log back, and do not keep swapping images to try your luck. Swapping an image is the most expensive dice roll there is; every swap repays a full round of environment time.

The second half is the complete specification: pre-boot checks, the three boot checks, environment and long-task discipline, the no-capacity fallback rule, the closing rules, the failure cap, and the stage-based result codes. Anyone operating a cloud GPU — or any AI assigned to boot one — can follow the whole set exactly as written.

The Complete Runbook Follows

1. Before Booting (P)

  • P1 Image: the official PyTorch image (CUDA 12.x series); startup arguments / Docker arguments left empty, with no command injected.
  • P2 Naming and single machine: machines booted by our side always use the agreed prefix; at most one GPU machine runs at a time.
  • P3 Capacity first: check capacity for the target GPU in the disk-bound datacenter before booting; booting without checking counts as unverified goods.

2. The Three Boot Checks (V, After Running; All Three Must Pass Before Any Task)

  • V1 The device-list command lists the target GPU.
  • V2 Compute check: the in-Python GPU-available check returns true.
  • V3 Disk check: the space listing is normal and the target disk is readable. If any item fails: hand over no task and diagnose first; in diagnosis, suspect the environment's read path first (environment files on the network disk), then version-versus-driver alignment.

3. Environment Discipline (E)

  • E1 Use the system Python and install packages onto the container's local disk; never build a virtual environment on the network disk.
  • E2 The network disk holds only models, datasets, and outputs; a model needing fast reads may be copied locally first.

4. Long-Task Discipline (L)

  • L1 Run long tasks as background residents (nohup- or tmux-style), with logs written to files and polled by tail, so a dropped connection cannot kill the task.
  • L2 Save a checkpoint every 250 steps, with its hash stored to disk or the repository, so an interruption can resume.

5. Capacity Fallback (F)

When the disk-bound datacenter shows no capacity, do not dry-wait: boot a machine with no disk attached, pull models and data again from public sources (model hub / code repository), and after the output is uploaded and confirmed, delete the machine.

6. Closing (T)

  • T1 Output confirmed saved before any shutdown is allowed.
  • T2 Terminate, do not stop; a stopped machine still bills storage.
  • T3 After terminating, list the machines and confirm deletion with your own eyes.
  • T4 Record this machine's cost in the version log.
  • T5 Idle over 15 minutes: close following T1 to T4; leave no machine spinning empty.

7. Failure Cap (R)

The same error retried 2 times and still failing: stop, hand the complete log back to the decision side, and do not keep swapping images to try your luck.

8. Common Mistakes Checklist

  • Injecting a stay-alive command into the startup arguments: it overwrites the image startup script, and remote login and initialisation never run.
  • Building a virtual environment on the network disk: the library-loading step stalls, and it gets misread as broken code.
  • Booting without a capacity check, then dry-waiting when there is no stock: pulling models on the fallback route usually costs less than waiting.
  • Handing over a task on "running" alone: without the three checks, the task only dies more expensively.
  • Closing with stop instead of terminate: you leave, and the storage meter keeps running.
  • Swapping images after the same error, again and again: every swap repays the environment time; at the two-retry cap, hand back the log.
