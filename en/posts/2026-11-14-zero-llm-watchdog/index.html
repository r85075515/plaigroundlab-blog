Prevention Must Not Become the Biggest Usage Line: Designing Zero-LLM Watchdogs

For your AI: this post ships with a clean-Markdown agent edition — read it and follow along: English · 中文版

Opening: The Story, Written for Humans

Every time an incident closes here, our rule is to fix not only the immediate problem but also automatically propose prevention for the same class of problem: add a probe, add a gate, add a fallback, add a reporting path. That rule has one natural enemy — itself. Prevention work is almost always repeated on a timer: look every five minutes, check every thirty minutes, scan once a day. If every single check wakes an AI to "take a look," the more diligently you check, the more you spend; the incident is prevented, but the bill is eaten by the guard. So on 2026-11-01 the team fixed a guardrail in place: prevention itself must not be allowed to become the biggest usage line.

The guardrail's default design fits in one sentence: anything that can be written as a dead script is built as a dead script, at zero LLM usage, and an agent is woken only when a failure threshold is actually triggered. A dead script is a deterministic program: fixed input, thresholds written in advance, an outcome it can judge by itself, and no semantic judgement anywhere in the loop. Its language-model usage per run is zero, and silence with no output is its normal state, not a missed job. The agent is woken only at a few kinds of moments — an edge transition, a failure streak reaching its mark, or an escalation threshold — deals with the matter, and goes back to sleep.

This is not a slogan; we rebuilt three real watchdogs this way.

The first was a GPU capacity sentinel. Under the old design, an agent schedule woke every thirty minutes to "take a look" at whether one graphics-card model was in stock; most of the time the answer was "no," and every look cost usage. On 2026-10-31 it was rebuilt as a dead-script hook: every 1,800 seconds it checks capacity itself, reads the number of tasks waiting to be dispatched, and writes back to the original state file, at zero LLM usage. Only two situations can wake an agent now: capacity moves from none to some while at least one task is waiting (an edge trigger, ringing once only), or the capacity query itself fails twice in a row (ringing once only, resetting automatically on recovery). At the switch, the new design was first run live for one round and verified to stay correctly silent before the old schedule was stopped, leaving no monitoring gap; the rough estimate was a saving of 15–20M raw tokens per day.

The second was a connectivity canary. Every five minutes a dead script walks the full public path as a self-test, and only a matching echoed nonce counts as truly through; segment health is recorded separately, so which segment died is visible at a glance. Two consecutive failures first trigger an automatic restart with a 45-second wait and a retest; six consecutive failures (about thirty minutes) are what it takes to escalate and wake an agent — and the wake-up must name which segment died, not just say "something seems broken."

The third was a worker-silence alert. A dead script checks active workers' heartbeats every thirty minutes: silence over 6 hours earns a first report, over 24 hours one follow-up, and a revival closes the alert automatically. After launch, one refinement was added: crossing a threshold first "seeds" a pending-confirmation state, and the alert is sent only if the next round (about 25 minutes later) still shows no heartbeat — so a worker halfway through reviving is not falsely reported. Its first real firing followed exactly that rhythm: seed, confirm on the next round, report once, no repeats afterwards, and automatic closure when the heartbeat returned.

The last piece is enforcement, deliberately built without any new audit system: prevention work must be identifiable and measurable inside the existing weekly usage self-scan — new items always carry the precaution- name prefix and every item is entered in one registry (existing items are not renamed, so their state files are not broken; the registry covers them instead); the self-scan totals sentinels, watchdogs, and guards as one separate line and computes a per-run estimated cost for each (its share of the period's usage divided by its number of runs). If prevention ever does become a major line, it shows up in the self-scan and gets pulled out and slimmed down. One comparison figure: in a self-scan on 2026-11-02, prevention work here totalled about 0.78% of all usage; a census of another ecosystem in the same period put prevention at about twenty percent — the difference is not how much is checked, but who does the checking.

The second half is the complete specification: the four eligibility conditions for dead-script form, the priority order of the five dispositions, the runtime trigger ladder (edge, streak, two-round confirmation, escalation, automatic closure), and the three usage-audit rules. Anyone adding a watchdog to their own system — or any AI assigned to design one — can follow the whole set exactly as written.

The Complete Runbook Follows

1. Dead-Script Eligibility (E): All Four Must Hold

Judge the check action itself, item by item: (a) the input source is fixed; (b) the rule can be written as an explicit threshold (a numeric threshold, a boolean test, or a state transition); (c) completion or failure can be judged by the program from the data alone; (d) no semantic judgement is needed anywhere in the check. All four holding records E = Y; any one failing records E = N. When the facts an item needs are not mentioned and cannot be directly inferred, record that item as "undetermined"; if any item is undetermined, always freeze the design first, and never guess a value in order to build directly.

2. Five Dispositions (Judged in Number Order; the First That Holds Is the Result)

Form Condition What to do
F1 Freeze first Any eligibility item undetermined Build nothing; complete the input, threshold, and judgement method, then re-run the judgement after freezing
F2 Do not duplicate The registry already has a live item with the same input source watching the same failure Build no new item; adjust the existing one if a change is needed
F3 Dead script (the default) E = Y Run on a timer at zero LLM usage; wake an agent only on a Section 3 trigger; silence is the normal state
F4 Hybrid The only reason E = N is (d): triggered cases need semantic judgement, while (a)–(c) hold for a pre-filter The dead script collects and filters (zero LLM) and wakes an agent only for the filtered subset; the agent never performs the routine scan itself
F5 Agent exception E = N, and even a pre-filter cannot be completed deterministically An agent schedule may run the check, but the reason must be registered, a review or expiry date must be set, and its usage is measured separately in the audit; this is an exception, not the default

The point of the priority order: undetermined freezes first, so nothing is built on guesses; duplication is intercepted next, so the same job never gets two dogs; whatever can be a dead script never becomes a hybrid, let alone an agent exception.

3. The Runtime Trigger Ladder (Applies to F3, and to the Script Part of F4)

Before a watchdog goes live, three parameters must be registered: the wake transition (which state transition triggers, with any companion conditions), the failure-streak wake threshold K (an integer, at least 2), and the escalation threshold K2 (may be unset; if set, it must be greater than K). No registration, no launch. Each run is judged in this order:

  • T1 Successful run: when a run successfully obtains and judges its data, the failure streak resets to zero; if a wake or report already happened and this is the first successful run after it, the alert closes automatically and the closure is logged; every other successful run is quiet (one structured log record only, no wake, no report).
  • T2 Edge wake: in a successful run, when a registered wake transition occurs and its companion conditions hold at the same time, wake once; later runs do not wake again while the state is unchanged, and counting restarts only after the state leaves and transitions again.
  • T3 Streak wake and escalation: a failed run (the probe cannot obtain its data or cannot judge it) adds one to the streak; the run on which the count exactly reaches K wakes once; streak runs above K and below K2 stay quiet and never re-wake; if K2 is registered, the run on which the count exactly reaches K2 wakes once as an escalation. A successful recovery follows T1: reset and closure.
  • T4 Below threshold: a failed run whose count is below K, with no other trigger hit, only logs and accumulates the count, quietly, with no wake.
  • T5 Two-round confirmation (only for items that registered it): when an item registers "confirm on the next run," the first run that reaches a T2 or T3 trigger only seeds a pending-confirmation state and does not wake; if the next run (at least one interval later) still shows the same condition, it wakes as T2 or T3 prescribes. Items that did not register it wake as soon as a trigger is reached; this rule does not apply to them.

Note that "a failed run" and "a successful run that finds something wrong" are different things: a probe that successfully obtains data and finds the watched state has transitioned is T2; a probe that cannot obtain its own data is a T3 failure. The two must never be counted into the same streak.

4. Usage Audit (Three Rules, and No New Audit System)

  • A1 Identifiable: every prevention item is entered in the registry; new items always carry the precaution- name prefix; existing items are not renamed (renaming could break their state files) and are covered by their registry entries instead.
  • A2 Measurable: the existing weekly usage self-scan totals prevention work as one separate line, and computes each item's per-run estimated cost as its share of the audit period's usage divided by its number of runs. Script runs under F3 and F4 record zero usage; usage from a woken agent run is counted toward that wake's handling work, not back-charged as script-run cost.
  • A3 Slimming flags: meeting any one of these flags the item in that period's self-scan for a slimming review — (i) an F5 exception item is still running past its registered review or expiry date; (ii) for an F3 or F4 item, woken runs make up more than half of its total runs in the audit period (a threshold so loose it is effectively an agent schedule); (iii) the audit finds it duplicating another registry item's source and failure. A flag does not mean immediate shutdown: thresholds, frequency, and form are reviewed first, then the item is rebuilt or retired.

5. Common Mistakes Checklist

  • Waking an agent every round to "take a look": the more diligently you check, the more you burn, and prevention itself becomes the biggest usage line.
  • Reporting the same state every round: with no edge trigger and no ring-once rule, report bombardment trains everyone to treat real alerts as noise.
  • Confusing probe failure with the watched target failing: being unable to fetch your own data and the other side actually being down are two different incidents with two different handling paths.
  • Firing the instant a threshold is crossed, with no confirmation round: false reports about a target halfway through recovery teach everyone to ignore the alarm.
  • Prevention items that are never registered or labelled: the usage self-scan cannot separate them out, so nobody can see them becoming a major line.
  • Building an audit schedule to audit the audits: borrowing the existing self-scan for enforcement is enough; a new audit becomes new prevention cost itself.
